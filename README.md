# #FursuitFryday

행사 사진에 **행사·작가**를 붙이고, 어느 컷을 **SNS에 올렸는지** 기록하는 도구.

- 서버 없음. 정적 파일만. 빌드 단계 없음.
- 저장소는 사용자 본인의 **구글 드라이브**, DB는 드라이브에 둔 **`fursuitfryday.catalog.json`** 한 파일.
- **사진 파일은 읽기만 한다.** 이 앱이 쓰는 건 catalog 하나뿐이라 원본이 상할 일이 없다.
- iOS 홈 화면에 추가해 웹앱으로 쓰는 것을 전제로 만들었다.

---

## 지금 바로 보기 (설정 없이)

```bash
python tools/devserver.py 5173
```

브라우저에서 **http://localhost:5173/?demo=1**

서버는 `0.0.0.0` 에 묶이고 시작할 때 폰에서 열 주소를 함께 찍어 준다. 같은 와이파이의 아이폰에서 그 주소로 접속하면 된다.

로그인도 드라이브도 없이, 샘플 사진 184장과 다가오는 일정 2건으로 앱 전체를 조작할 수 있다. 일정 날짜는 여는 날 기준 상대 날짜라 언제 열어도 디데이가 말이 된다. 사진은 캔버스로 그린 것이고 네트워크를 쓰지 않는다. **행사·작가가 하나도 지정되지 않은 상태**로 시작하므로, 실제 첫 사용 경험(제안 → 분류)을 그대로 확인할 수 있다.

아이폰에서도 같은 주소로 접속해 홈 화면에 추가하면 웹앱 조작감을 미리 볼 수 있다. (같은 와이파이에서 `http://<PC IP>:5173/?demo=1`)

## 설정 (실제 드라이브 연결) — 약 5분

### 1. Google Cloud Console

<https://console.cloud.google.com/>

1. 상단 프로젝트 선택 → **새 프로젝트** → 이름 `fursuitfryday` (또는 원하는 이름) → 만들기
2. **API 및 서비스 → 라이브러리** 에서 두 개를 사용 설정
   - `Google Drive API`
   - `Google Picker API`
3. **API 및 서비스 → OAuth 동의 화면**
   - User Type: **외부**
   - 앱 이름 `#FursuitFryday`, 지원 이메일 본인
   - 범위 추가는 **하지 않아도 된다** (앱이 요청할 때 결정된다)
   - 테스트 사용자에 본인 이메일 추가
   - ⚠️ **마지막에 "앱 게시"까지 누르세요.** 테스트 상태로 두면 리프레시 토큰이 7일 뒤 만료됩니다. 게시해도 검증은 필요 없고, `drive.file` 은 민감하지 않은 범위라 경고 화면도 뜨지 않습니다.
4. **API 및 서비스 → 사용자 인증 정보 → 사용자 인증 정보 만들기**
   - **OAuth 클라이언트 ID** → 애플리케이션 유형 **웹 애플리케이션**
   - **승인된 자바스크립트 원본**
     - `http://localhost:5173`
     - `https://<사용자명>.github.io`
   - **승인된 리디렉션 URI** — 문자 하나까지 정확해야 한다. 끝의 `/` 포함.
     - `http://localhost:5173/`
     - `https://<사용자명>.github.io/cutdaejang/`
   - 만들고 나온 **클라이언트 ID** 를 복사
   - 이어서 **사용자 인증 정보 만들기 → API 키** 도 하나 만들어 복사 (Picker 용)

### 2. config.js

```bash
cp config.example.js config.js   # 이미 있으면 생략
```

`config.js` 를 열어 `CLIENT_ID` 와 `API_KEY` 를 붙여넣는다. `config.js` 는 `.gitignore` 에 있어 커밋되지 않는다.

### 3. 실행

```bash
python tools/devserver.py 5173
```

<http://localhost:5173/> → **구글로 시작하기** → 폴더 고르기 → 동기화

## GitHub Pages 배포

**HTML 한 개가 아니다.** ES 모듈로 나뉘어 있고, 서비스 워커는 규격상 별도 파일이어야 한다. 아래를 **폴더째** 올린다. 빌드 단계는 없으니 파일을 그대로 올리면 그게 곧 배포본이다.

```
index.html  app.css  sw.js  manifest.webmanifest  config.js  .nojekyll
icons/    ← PNG 4개
js/       ← 모듈 16개
```

`tools/`, `serve.ps1`, `README.md` 는 올려도 되고 안 올려도 된다(동작과 무관).

```bash
git add -A
git commit -m "#FursuitFryday"
git branch -M main
git remote add origin https://github.com/<사용자명>/cutdaejang.git
git push -u origin main
```

저장소 **Settings → Pages → Source: Deploy from a branch → main / (root)**. 1~2분 뒤 `https://<사용자명>.github.io/cutdaejang/` 에 뜬다.

### 알아둘 것

- **`config.js` 는 커밋한다.** `.gitignore` 에서 뺐다. `CLIENT_ID` 와 `API_KEY` 는 Cloud Console 의 "승인된 원본"·리퍼러 제한으로 보호되는 값이라 공개돼도 다른 사이트에서 쓸 수 없다. 반대로 올리지 않으면 배포본이 이 파일을 못 찾는다 — `config-load.js` 가 없어도 앱은 뜨지만(데모는 동작) 실제 연결은 안 된다. **API 키에는 Cloud Console 에서 HTTP 리퍼러 제한을 걸어 두자.**
- **키를 안 넣어도 배포는 된다.** `?demo=1` 은 바로 동작하니, Cloud Console 설정은 나중에 해도 된다.
- **`.nojekyll`** 이 있어야 GitHub 가 Jekyll 처리를 건너뛴다.
- **하위 경로에 배포된다** (`/cutdaejang/`). 모든 참조가 `./` 상대 경로여서 그대로 동작한다. 절대 경로(`/js/…`)를 추가하지 말 것.
- **OAuth 리디렉션 URI** 에 배포 주소를 **끝의 `/` 까지** 정확히 등록해야 한다: `https://<사용자명>.github.io/cutdaejang/`
- **`sw.js` 의 `V` 를 배포할 때마다 올린다.** 네트워크 우선이라 치명적이지 않지만, 오프라인 셸이 옛 파일에 묶이지 않는다.
- **업데이트가 바로 안 보인다.** Pages CDN 캐시(약 10분) + 서비스 워커가 옛 셸을 내주기 때문이다. 홈 화면 웹앱을 완전히 닫았다 열면 새 버전이 붙는다.

## iOS 웹앱으로 쓰기

사파리에서 배포 주소를 열고 **공유 → 홈 화면에 추가**.

알아둘 것:

- 홈 화면 웹앱은 **사파리와 저장소가 분리**되어 있다. 사파리에서 로그인했어도 웹앱 안에서 한 번 더 로그인해야 한다.
- 반대로 홈 화면 웹앱은 사파리의 7일 저장소 삭제 정책에서 제외되는 것으로 알려져 있어, 토큰과 키가 유지된다.
- 로그인은 **팝업이 아니라 전체 페이지 리다이렉트**로 구현했다. standalone 모드에서 팝업이 새는 문제를 피하기 위한 것이다. 로그인할 때 화면이 통째로 넘어가는 건 정상이다.
- **수백 장 임포트는 데스크톱에서** 하는 것이 안전하다. iOS 는 탭이 백그라운드로 가면 자바스크립트를 재우기 때문에, 화면을 끄면 동기화가 멈춘다.

### 반드시 먼저 확인할 것

1. 배포 후 아이폰 사파리에서 접속 → 로그인 성공
2. **홈 화면에 추가한 뒤** 웹앱을 열어 다시 로그인 → 성공
3. 폴더 고르기(Picker)가 웹앱 안에서 열리는지

2번과 3번이 이 프로젝트에서 가장 불확실한 지점이다. 여기서 막히면 알려주면 대응책을 넣는다.

## 폴더 권한이 안 열릴 때

`drive.file` 스코프는 원래 "앱이 만든 파일과 사용자가 피커에서 직접 고른 항목"만 허용한다. 피커에서 **폴더**를 골랐을 때 그 하위 파일까지 열리는 것에 의존하고 있는데, 계정·조직 설정에 따라 안 될 수 있다.

동기화가 `403`/`404` 로 실패하면 앱이 이 상황을 알려준다. 그때 선택지:

1. 피커에서 폴더 대신 **파일을 직접 다중 선택** (수백 장은 비현실적)
2. `config.js` 의 `SCOPE` 를 `https://www.googleapis.com/auth/drive.readonly` 로 바꾼다 — 드라이브 전체를 읽을 수 있게 되지만 **제한된 범위**라 구글 검증 없이는 "확인되지 않은 앱" 경고가 뜨고 사용자 100명 상한이 걸린다. 개인·소규모 팀 용도로는 감당 가능하다.

### 설계 규칙 몇 개

- **catalog 의 키는 Drive fileId, 보조 키는 md5.** 파일명·폴더가 바뀌어도 태그가 살아남고, 지웠다 다시 올려 fileId 가 바뀌어도 md5 로 옛 기록에 다시 붙는다.
- **사라진 사진의 기록은 지우지 않는다.** `gone` 으로 옮겨 보존한다. 원본이 없어져도 "이걸 올렸다"는 사실은 유효하다. 사용 이력이 있는 사진이 사라지면 경고를 띄운다.
- **비밀은 catalog 에 넣지 않는다.** unavatar 키는 기기 `localStorage` 에만 둔다. 나중에 공유 드라이브로 팀 공유하면 catalog 는 팀 전체가 읽기 때문이다.
- **자동 분류는 사용자가 켠 규칙만.** 두 작가가 같은 바디를 쓰면 틀리므로 기본은 항상 묻는다.
- **태그는 설정에서만 만든다.** 사진에 달 때는 고르기만 해서 오타로 태그가 갈라지지 않는다. 기본 태그는 비어 있다 — 필요한 것만 직접 만든다.
- **세그먼트 알약은 CSS 변수로만 움직인다.** `offsetWidth` 를 재지 않으므로 웹폰트가 늦게 떠도 어긋나지 않고, 폭을 트랜지션하지 않으므로 이동 중에 찌그러지지 않는다.
- **다시 그릴 때 스크롤을 보존한다** (`keepScroll`). 제안 카드 하나를 처리했을 때 목록이 최상단으로 튀지 않는다.
- **탭은 네 개까지.** 홈 · 사진 · 일정 · 설정. 목록 성격의 화면(태그로 찾기)은 탭이 아니라 설정 안의 푸시 화면으로 둔다.
- **행사 = 일정.** 같은 목록을 사진 분류 축과 일정으로 겸용한다. 일정에서 만든 행사가 사진 분류에 바로 쓰이고, 반대도 같다.
- **체크리스트는 두 갈래.** `사전 준비` 는 그 행사만의 할 일(행사별), `짐 챙기기` 는 매번 같은 것이라 공용 목록(`cat.packing`)을 설정에서 관리하고 체크 상태만 행사별(`events[].packed`)로 남긴다.
- **클래스 이름 충돌을 조심한다.** 맨몸 `.pill` / `.num` 같은 선택자는 다른 화면과 부딪힌다. 실제로 세그먼트 알약이 사진 상세의 상태 배지(`.pill{height:28px}`)에 눌려 찌그러진 버그가 있었다 — 지금은 `.seg .knob` 으로 분리했다.
- **썸네일은 IndexedDB 에 남긴다.** 메모리만 쓰면 앱을 다시 열 때마다 전부 다시 받아 그리드가 느리게 채워진다. 400px 썸네일만 저장하고(장당 30~60KB), 목록을 그린 직후 `warm()` 으로 한 트랜잭션에 읽어 첫 화면을 즉시 채운다. 원본은 캐시하지 않는다.
- **행사는 하루짜리도 여러 날짜리도 된다.** `date`~`endDate`. 진행 중이면 `2일차 / 3일 중`으로 세고 카드가 초록으로 바뀐다.
- **행사 안의 약속은 하위 일정(`sub`)으로 둔다.** 별개 행사로 만들면 사진 분류 축이 쓸데없이 늘어난다. 여러 날 행사면 며칠차로 묶어 보여주고, 약속마다 메모를 붙일 수 있다. 목록에서 약속을 누르면 읽기 시트가 뜬다(편집은 일정 상세에서).
- **참가 확정(`going`)이 아닌 행사는 홈 디데이를 차지하지 않는다.** 갈까 말까 하는 행사를 등록만 해두기 위한 것. 우선순위는 진행 중 > 다가오는 확정 > 다가오는 미정.
- **펼침 패널은 `max-height` 를 재서 넣는다.** 내용 높이가 제각각이라 CSS 만으로는 안 되고, 펼친 상태는 모듈 `Set` 에 남겨 다시 그려도 유지한다.
- **행사 로고는 이미지, 디데이와 자리를 나눈다.** 로고는 128px WebP base64 로 catalog 에 넣고(장당 4~8KB), 목록 행은 **왼쪽 = 로고 또는 대표사진 / 오른쪽 = 디데이**로 자리를 분리한다. 로고를 넣어도 디데이가 가려지지 않는다.
- **`사진사 미상` 은 미지정과 다르다.** 알아본 뒤 모른다고 결론 낸 상태라 실제 사진사 항목(`s-unknown`)으로 두고, 미분류에서 빠지되 카메라→사진사 학습과 크레딧 복사에서는 제외한다.
- **진입 애니메이션은 앞으로 나올 때 되돌린다.** `.stagger` 는 fill-mode both 라 백그라운드에서 그려지면 opacity 0 으로 남는다. `visibilitychange` 에서 클래스를 다시 걸어 반드시 끝까지 재생시킨다.
- **테마 색은 `--blue` 계열 토큰만 갈아끼운다.** 액센트가 그 세 토큰에 모여 있어서, `[data-accent]` 블록으로 라이트·다크를 각각 정의하면 시스템 테마 전환도 알아서 따라간다.
- **탭 선택 알약은 하나를 옮긴다.** 탭마다 알약을 두면 슬라이드가 불가능하다. `#tabbar` 에 `--i` 만 갱신해 공유 알약을 `translateX(calc(var(--i) * 100%))` 로 옮기고, 이동은 스프링(`cubic-bezier(.34,1.56,.64,1)` 520ms)으로 오버슈트시킨 뒤 도착에 맞춰 `scale` 을 부풀렸다 가라앉힌다("슥 뽕"). 움직이는 동안만 스펙큘러를 켜고 위쪽 고인 빛을 줄인다. **그래서 탭바는 한 번만 만들고 이후엔 클래스와 `--i` 만 바꾼다** — 매번 `innerHTML` 을 새로 쓰면 알약이 새로 생겨나 슬라이드가 사라진다.
- **유리는 맑아야 유리다.** `blur` 를 세게 먹이면 서리 유리가 된다. 애플의 리퀴드 글라스는 roughness 0 — 유리처럼 보이게 하는 건 ① 가장자리 굴절 ② 색수차 ③ 테두리 스펙큘러 세 가지다. 그래서 `blur` 는 계단 현상만 지울 0.3 으로 두고 굴절과 색수차로 만든다.
- **굴절은 SVG 변위 맵으로.** 캔버스로 맵을 그려(R=X 이동, G=Y 이동, 128 중립) `feDisplacementMap` 에 물리고 그 필터를 `backdrop-filter: url(#…)` 로 쓴다. 베젤 프로필은 라운드 사각형 SDF 로 재서 테두리 16px 안쪽까지만 곡면(`pow(u,2.4)`)이고 가운데는 변위 0 — 그래서 중앙은 맑게 통과한다.
- **색수차는 같은 맵을 배율만 달리해 세 번.** 파장이 길수록 덜 꺾이므로 R:1.00 G:0.91 B:0.82 로 돌리고, 각각에서 한 채널만 남겨 다시 더한다. ⚠️ 이때 `feColorMatrix` 의 **알파를 상수 1 로 고정**해야 한다. 원본 알파를 두면 세 장을 더할 때 알파가 3배로 쌓이고 프리멀티플라이드 합성이 어긋나 화면 전체에 분홍 끼가 돈다 — 실제로 겪은 버그다.
- **⚠️ SVG 필터를 `backdrop-filter` 로 받는 건 크로미움만 된다.** 사파리는 지원하지 않으므로 아이폰에서는 이 효과가 안 걸린다. `navigator.userAgentData.brands` 로 갈라 `html.glass-svg` 를 붙이고, 사파리는 **맑은 CSS 유리**를 쓴다 — 굴절을 흉내내려 blur 를 세게 먹이면 서리 유리가 되니, 반대로 blur 를 6px 로 낮추고 테두리 14px 밴드의 밝기·채도만 올린다. 유리답게 보이는 핵심은 두께가 만드는 **테두리 안쪽의 얇은 어두운 선**이다. 두 경로를 겹치면 이중으로 흐려져서 SVG 경로에서는 CSS blur 와 `::before` 링을 물린다.
- **탭 아이콘은 선택되면 속이 채워진다.** 윤곽선 아이콘에 `fill` 을 그냥 주면 열린 경로가 엉뚱하게 메워지므로 탭 네 개는 채운 변형을 따로 그렸다(`icFill`). 두 변형을 겹쳐 두고 opacity·scale 로 교차시킨다.
- **아이콘 구멍은 `fill:none` 이어야 한다.** sliders 노브를 `fill:var(--bg)` 로 칠해 구멍을 흉내내면 유리 위에서 흰 덩어리로 보인다 — 선에 이미 빈 구간이 있으니 fill 을 주지 않는 게 진짜 구멍이다.
- **탭바와 알약은 완전한 캡슐이다.** `border-radius:999px`. 굴절 맵도 같은 모양이어야 하므로 `radius:999` 를 넘기면 `glass.js` 가 높이의 절반으로 잘라 캡슐 SDF 를 만든다.
- **선택된 칸은 밝아지지 않고 어두워진다.** 흰 알약을 얹으면 "덮은 판" 이 되고, 애플의 리퀴드 글라스에서 선택된 칸은 **유리가 한 겹 더 겹친** 것처럼 읽힌다. 그래서 `backdrop-filter:brightness(.93)` 로 뒤를 눌러 어둡게 하고, 위에서 드리운 그림자를 `inset` 으로 넣고 **아래 립에만** 빛을 남긴다(그림자가 위에서 오니 빛은 아래에 고인다).
- **다시 그리면 애니메이션이 죽는다 — 세 곳에서 같은 실수를 했다.** 탭바 알약, 토글 스위치, 모아보기 축 세그먼트. 모두 조작할 때 화면 전체를 `innerHTML` 로 다시 그려 요소가 새로 생기는 바람에 슬라이드가 사라졌다. 규칙: **조작한 요소는 제자리에 두고 클래스·CSS 변수만 바꾸고, 영향받는 다른 부분만 따로 갱신한다.** 모아보기는 `#home-groups` 만 다시 그린다(`paintGroups`).
- **행사 상세의 사진사 제안은 카메라 모델로 묶는다.** 같은 바디로 찍힌 사진은 대개 같은 사진사이므로 `Canon EOS R6 Mark II · 32장 → 사진사 지정하기` 로 묶어 보여준다. 여기서 한 번 지정하면 홈의 카메라→사진사 제안이 학습할 씨앗이 된다 — 새 카탈로그에서 제안이 부트스트랩되지 않는 문제를 이걸로 푼다. (일정 탭의 행사 상세와 모아보기의 행사 그룹 상세는 서로 다른 화면이다. 둘 다 넣었다.)
- **토글은 제자리에서 뒤집는다.** 누를 때 화면을 다시 그리면 스위치가 새 상태로 갑자기 나타나 애니메이션이 사라진다. `flipSwitch()` 로 클래스만 뒤집고 그 행의 문구만 갈아 준 뒤, 영향받는 다른 화면만 갱신한다. 트랙은 눌린 홈(오목), 비드는 볼록한 유리알 — 위치 이동은 `.sw i`, 늘어남은 `::before` 가 맡아 `transform` 이 부딪히지 않는다.
- **알약은 물방울처럼 늘어난다.** 이동 거리에 비례하는 `--sx` 와 방향 `--dir` 을 넘겨, 출발할 때 진행 방향으로 늘어나며 살짝 기울고(skew) 도착에서 눌렸다가 되튄다. 늘어남은 1칸 0.20 → 3칸 0.36.
- **맑은 유리 위 글자는 그림자로 지킨다.** 흐림이 없으니 배경이 그대로 보여 라벨이 묻힌다. 글자와 아이콘을 거의 검정(`--g900` 76%)으로 두고, 비활성 탭에만 얇은 `text-shadow` 와 아이콘 `drop-shadow` 를 준다(iOS 도 이렇게 한다). 선택된 탭은 알약이 받쳐 주므로 그림자를 빼고 완전 불투명하게 쓴다.
- **레이어드 CSS 유리(사파리 경로)는 네 겹이다.** 본체가 볼록한 돔(위 하이라이트 → 아래 음영), `::before` 가 테두리에서 `--bezel-w:14px` 만 남긴 베젤 링으로 여기서만 `blur`·`saturate`·`brightness` 를 올려 굴절을 만들고, `::after` 가 1.2px 테두리에만 도는 스펙큘러다. 링은 `mask-composite:exclude` 로 가운데를 파낸다. 유리는 뒤에 뭔가 지나가야 유리로 보이므로 `position:absolute` 로 띄우고 스크롤에 아래 여백을 준다. `backdrop-filter` 를 못 쓰는 환경에서는 `@supports not` 으로 불투명하게 되돌린다 — 글자가 안 보이면 안 된다.
- **X 는 `https://x.com/...` 로 연다.** iOS 유니버설 링크가 X 앱으로 넘겨준다. `twitter://` 스킴을 직접 던지면 앱이 없을 때 사파리가 오류 대화상자를 띄운다.

## 2차로 남긴 것

- **pHash 유사 컷 묶음** — 연사 중 어느 컷을 올렸는지 구분하는 기능. 1,000장 넘는 해시 계산을 아이폰에서 돌릴 수 없어 데스크톱 첫 동기화를 전제로 따로 설계해야 한다.
- **업로드** — 원본은 드라이브에 직접 올리는 것이 빠르고 안전하다. 현장에서 폰으로 찍은 사진 추가 정도로 좁게 넣을 여지가 있다.
- **공유 드라이브 기반 팀 공유** — catalog 를 공유 드라이브에 두면 팀 공유가 되고 개인 15GB 를 쓰지 않는다. 동시 편집 충돌 처리는 `store.js` 에 이미 들어 있다.
